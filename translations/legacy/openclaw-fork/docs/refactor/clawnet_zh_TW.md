# Clawnet 重構 (協定與驗證統一)

## 計畫目的
建立一份嚴謹的文件，描述網路架構的現狀、痛點以及提議的新狀態：統一協定、限定範圍的角色、統一的驗證/配對機制以及 TLS 固定 (Pinning)。

## 核心目標
- **單一協定**：適用於所有客戶端（Mac App, CLI, iOS, Android, 無頭節點）。
- **身分核實**：每個網路參與者都必須經過驗證與配對。
- **角色清晰**：區分 **節點 (Nodes)** 與 **操作者 (Operators)**。
- **中央核准**：將核准請求路由至使用者目前所在的裝置。
- **全面 TLS**：所有遠端流量皆加密並支援選用的固定 (Pinning) 機制。

## 提議的新狀態 (Clawnet)

### 單一協定，兩種角色
使用單一 WebSocket 協定，並透過「角色」與「權限範圍」區分權限。

- **角色：節點 (Node)**
  - 能力：宣告指令（如 `system.run`）、接收調用、發送事件。
  - 限制：無法存取組態、模型、頻道或工作階段管理 API。
- **角色：操作者 (Operator)**
  - 能力：完整的控制平面 API（受限於權限範圍）。
  - 範圍：`read` (讀取), `write` (執行), `admin` (管理), `approvals` (核准)。

### 統一驗證與配對
- **裝置身分**：每個客戶端提供穩定的 `deviceId`（衍生自金鑰對）。
- **配對流程**：客戶端以未驗證身分連線 → 閘道器建立配對請求 → 操作者在 UI 上核准 → 閘道器發放綁定金鑰的憑證。

### 中央化核准設計
- **現狀**：核准發生在執行指令的節點主機上。
- **提議**：核准由 **閘道器託管**，並將 UI 派發至所有活動中的操作者客戶端。
- **優點**：不論指令在何處執行，核准提示都會出現在使用者手邊的裝置（如手機或 Mac）。

## 遷移策略
- **階段 1**：在 WS 協定中加入角色與權限範圍。
- **階段 2**：維持 Bridge 橋接器運作，並行開發 WS 節點支援。
- **階段 3**：實作中央化核准機制。
- **階段 4**：統一 TLS 實作。
- **階段 5**：棄用並移除舊版 Bridge 協定。
